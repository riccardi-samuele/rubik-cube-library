# Fast Blocked Faces Design

## Goal

Add a complete public-library option for `SolveMode::Fast` that lets callers
exclude one face, or two opposite faces, from every move generated by the fast
solver.

The first implementation supports the restriction only for `SolveMode::Fast`.
Requests that combine blocked faces with `SolveMode::Optimal` return
`SolveStatus::UnsupportedOptions` until constrained optimal solving is designed
separately.

## User Contract

Callers can provide zero, one, or two blocked faces.

- Zero blocked faces preserves the current behavior.
- One blocked face removes all turns of that face, including clockwise,
  half-turn, and inverse moves.
- Two blocked faces are valid only when the faces are opposite: `U/D`, `R/L`,
  or `F/B`.
- Duplicate blocked faces are invalid.
- Non-opposite two-face combinations are invalid.
- More than two blocked faces are invalid.

Invalid blocked-face configurations return `SolveStatus::UnsupportedOptions`.
If the configuration is valid but the restricted fast search does not find a
solution within `maxDepth` or `timeout`, the solver keeps the existing fast-mode
statuses: `DepthLimitExceeded` or `Timeout`.

## Public API

Extend `rubik::SolveOptions` with a public field:

```cpp
std::vector<Face> blockedFaces;
```

The field belongs in `include/rubik/solver.hpp`, next to the other solve-policy
options. It is intentionally a face-level restriction rather than a move-level
restriction because the requested product behavior is "do not move these faces".

Extend the experimental two-phase option types so the fast solver can pass the
same restriction through its existing phase-1 and phase-2 attempts:

```cpp
struct Phase1Options {
    int maxDepth = 12;
    std::chrono::milliseconds timeout{0};
    SolveProfile profile = SolveProfile::Default;
    std::size_t maxCandidates = 1;
    std::vector<Face> blockedFaces;
};

struct Phase2Options {
    int maxDepth = 18;
    std::chrono::milliseconds timeout{0};
    SolveProfile profile = SolveProfile::Default;
    std::vector<Face> blockedFaces;
};
```

These additions are public because `phase1` and `phase2` are already exposed as
experimental APIs. They must use the same validation rules as `SolveOptions`.

## CLI Contract

Add `rubik-solve` support:

```sh
rubik-solve <54-stickers> --mode fast --blocked-faces U,D
```

Rules:

- Values are comma-separated face letters.
- Valid face letters are `U`, `R`, `F`, `D`, `L`, and `B`.
- Empty values, duplicate values, invalid face letters, and more than two faces
  are rejected during CLI parsing with exit code `2`.
- Valid but unsupported solver combinations, such as blocked faces with
  `--mode optimal`, reach the solver and print `status: UnsupportedOptions`.

`rubik-bench` is not a required public surface for the first implementation
because the user-facing solve path is `Solver::solve` and `rubik-solve`.
If restricted fast-solving benchmarks are needed later, `rubik-bench` should
reuse the same parser and library option instead of introducing a separate
contract.

## Internal Move-Set Design

Introduce a small reusable internal move-set helper. The helper should:

- Validate blocked-face lists.
- Decide whether two faces are opposite.
- Build the allowed move list by filtering `rubik::allMoves()`.
- Expose a compact predicate for tests and CLI verification where useful.

The helper can initially live in `src/solver.cpp` if only the solver uses it,
but the preferred implementation is a focused internal module if phase1 and
phase2 also need the same logic:

- `include/rubik/detail/move_restrictions.hpp`
- `src/move_restrictions.cpp`

This keeps validation and filtering rules in one place instead of duplicating
them across `solver.cpp`, `phase1.cpp`, `phase2.cpp`, and CLI parsing.

## Solver Flow

`Solver::solve` validates blocked faces before entering search.

If `blockedFaces` is non-empty and the requested/effective mode is not
`SolveMode::Fast`, return `UnsupportedOptions`.

For `SolveMode::Fast`, build the allowed move list once and pass it through the
entire fast path:

- `twoPhaseAttempt`
- `findPhase1Candidates`
- `solvePhase2`
- `fastBeamSearch`

All fast-mode move generation loops must iterate over the allowed move list, not
over `allMoves()`.

## Phase 1 Behavior

`findPhase1Candidates` uses the allowed move list derived from
`Phase1Options::blockedFaces`.

The lower bound remains unchanged because it is still admissible under a
restricted move set: a lower bound computed for the unrestricted graph cannot
overestimate the restricted distance. It may become weaker, which is acceptable
for the fast solver.

The returned phase-1 candidate sequences must not contain moves on blocked
faces.

## Phase 2 Behavior

`solvePhase2` already has a fixed phase-2 move set:

```text
U U2 U' D D2 D' R2 F2 L2 B2
```

With blocked faces, phase 2 uses the intersection between this phase-2 set and
the allowed move list. For example, blocking `U,D` leaves only
`R2 F2 L2 B2`.

The phase-2 lower bound remains unchanged for the same reason as phase 1: it is
admissible but can be weaker for the restricted graph.

## Testing Strategy

Add tests at four levels.

1. Public solver API:
   - A small fast scramble with `blockedFaces = {Face::U}` returns `Found` or
     `Solved`, applies cleanly, and contains no `U`-face moves.
   - `blockedFaces = {Face::U, Face::D}` is accepted for fast mode.
   - `blockedFaces = {Face::U, Face::R}` returns `UnsupportedOptions`.
   - `blockedFaces` with optimal mode returns `UnsupportedOptions`.

2. Experimental phase APIs:
   - `findPhase1Candidates` returns candidates with no blocked-face moves.
   - `solvePhase2` returns a solution with no blocked-face moves for a small
     phase-2-valid scramble where such a solution exists.

3. CLI parsing:
   - `--blocked-faces U,D` is accepted.
   - `--blocked-faces X`, `--blocked-faces U,U`, empty values, and more than two
     faces are rejected with exit code `2`.
   - `--mode optimal --blocked-faces U` prints `status: UnsupportedOptions`.

4. Regression:
   - Existing fast-mode behavior without blocked faces continues to pass.
   - Existing optimal-mode behavior without blocked faces is unchanged.

## Documentation

Update public docs:

- `README.md`: add a short fast-mode example using `--blocked-faces`.
- `docs/api.md`: document `SolveOptions::blockedFaces`, valid combinations,
  current fast-only support, and status behavior.
- `docs/roadmap.md`: note that constrained optimal solving is future work and
  that the current feature is fast-mode only.

Do not publish any performance claim for restricted fast solving until benchmark
evidence exists.

## Non-Goals

- Do not implement constrained `SolveMode::Optimal` in this change.
- Do not add a new `SolveStatus`.
- Do not change the meaning of `SolveStatus::Optimal`.
- Do not add hardware or latency claims.
- Do not add arbitrary per-move restrictions; this feature is face-level only.
